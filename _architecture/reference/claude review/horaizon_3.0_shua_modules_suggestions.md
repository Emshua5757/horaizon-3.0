# horAIzon 3.0 — SHUA Sub-Modules Suggestions & Criticism

Covers `shua_diary` (TASK-017/018), `shua_resume` (TASK-020), `shua_code_visualizer` (TASK-015), `shua_gym`/`shua_crypto` (TASK-022/023, unwritten), and `shua_portal` (TASK-014).

---

## 1. There is no backup or disaster-recovery story anywhere in the plan

Across the entire compiled context — every spec, every task, every ADR — there is not one mention of backup, redundancy, snapshotting, or disaster recovery. And the stakes here aren't abstract: `shua_diary` is explicitly your personal journal, with a deduplicated media vault storing photos/videos, and `shua_crypto` is planned as a *key manager for a decentralized vault*. Both of those categories of data are the kind you cannot get back if the Pi 5's SD card or SSD fails, and SD card failure on a Pi that's "always-on" per the Governor spec is a genuinely common failure mode, not a hypothetical one.

Concretely, right now: `shua_diary.db` (SQLite), the entire `/var/lib/horaizon/media/` content-addressed store, and eventually the crypto vault all live on one piece of storage with zero copies anywhere else. I'd treat this as the single highest-priority planning gap in the whole document set — worth deciding *before* TASK-017 starts writing real diary entries into a database that has no backup plan, since "add backups later" tends to mean "after I've already lost something." Even a simple nightly `rsync`/`restic` of `/var/lib/horaizon/` to the Windows laptop or a cloud object store, run by the same Dream Loop scheduler that already exists for other nightly jobs, would close most of the gap with minimal new infrastructure.

## 2. Five backend languages for a one-person team is worth reconsidering, or at least naming as a deliberate cost

Counting what's actually planned: **Rust** (`shua_governor`, `shua_code_visualizer`), **Go** (`shua_resume`), **TypeScript/Node** (`shua_diary`), **Python** (`shua_gym`, `shua_crypto`), and **C#** (`shua_portal`, though that one's explicitly a learning side-project). That's four production languages plus a fifth for the interview-prep tool, each with its own toolchain, dependency ecosystem, build/lint/test setup, and idioms to keep warm in your head as a solo engineer. ADR-001 was explicit and thoughtful about cutting *architectural* complexity (SDUI) specifically because solo-engineering across multiple modules was "an unsustainable context-switch tax" — but that same reasoning doesn't seem to have been applied to language choice, which is arguably a bigger context-switch cost than UI architecture ever was. Worth being honest about why each language was picked (Go for `shua_resume` presumably for a specific reason — Typst tooling? binary size?) versus whether some of these could consolidate. Even if the answer after reflection is "no, each language is the right tool for that specific module and I accept the cost," it's worth writing that reasoning down the way ADR-001 did for the UI decision, rather than leaving it as an emergent property of the roadmap.

## 3. `shua_diary`'s task file implements a different wire contract than its own schema defines

(Covered in more depth in the main review doc, repeated here because it's specifically a diary-module issue.) `hbp_diary.toml` — the schema of record — defines `entry.create`, `entry.list`, `entry.get`, `entry.delete`, `block.save`, `block.reorder`, `block.delete`, `sentiment.score`, and `memory.elevate`. TASK-017's own RPC operations table implements `entry.save` (not `entry.create`) and adds `diary.search`, `diary.media.upload`, `diary.media.get`, and `diary.entry.updated` — none of which exist in the schema. Fix `hbp_diary.toml` to match what TASK-017 actually needs to expose (particularly the media vault operations, which are a whole subsystem TASK-017 describes in detail but the schema doesn't know about at all) before implementation starts, so the auto-generated Dart/TS types actually cover the real API surface.

## 4. The media vault's ref-counted delete has a narrow but real correctness gap
`media_vault.ts`'s dedup logic: upload computes SHA256, increments `ref_count` if it exists, and on block delete, decrements `ref_count` and deletes the physical file at `ref_count === 0`. That's a reasonable content-addressable design. But there's no mention of what makes the decrement-and-delete atomic with the block deletion itself — if the block row is deleted, the server crashes before decrementing `ref_count`, and restarts, that media file's ref count is now permanently overcounted by one, meaning it will never actually be deleted from disk even after every referencing block is gone (a slow disk-space leak), or conversely if the ordering is reversed, a file could be deleted while a block row still references it (a broken image in your diary). Worth explicitly wrapping the ref-count decrement and the block delete in a single SQLite transaction, and noting that in TASK-017 — `better-sqlite3` supports this cleanly and it's a small addition now versus a confusing bug to chase down later.

## 5. `shua_resume`'s Typst dependency is a single point of failure for the one module explicitly meant to produce time-sensitive output
The whole point of `shua_resume` is presumably to produce a tailored PDF resume when you need one — for a job application, i.e., often on a deadline. That entire pipeline depends on a Typst binary being correctly installed and working on the Pi 5 (or wherever compilation happens). There's no fallback path mentioned if Typst compilation fails (bad template, Typst version mismatch after an update, etc.) — no "here's how you get your resume out anyway" story. Given this module exists specifically to be useful under time pressure, it's worth having a documented manual fallback (e.g. "if `resume.compile` fails, the raw resume matrix JSON can be exported and formatted manually") rather than leaving PDF generation as the only path to the actual deliverable.

## 6. `shua_portal` (TASK-014) is scope-creep dressed as a roadmap item, worth deliberately separating
This is a smaller point, but: TASK-014 is an ASP.NET Core interview-prep simulator for practicing C#/EF Core concepts for job interviews. It's a genuinely good idea as a personal learning project — but it doesn't integrate with HBP v2, doesn't appear in the Flutter client's route tree, isn't part of the "personal AI OS" product the rest of the roadmap is building, and its own acceptance criteria don't mention the Governor, MCP, or any other horAIzon subsystem at all. It's sitting in `master_task_roadmap.md` labeled "Phase 3 — Learning & Integration" next to product-critical work like the diary backend, with the same `TASK-0XX` numbering scheme, which makes it look like part of the critical path when it structurally isn't blocking or blocked by anything. Worth either (a) moving it to a clearly separate "side projects" list so it doesn't compete for roadmap attention with things that actually block other tasks, or (b) if the intent *is* eventual integration (e.g. Governor tracks it as a module too), writing that integration path down so it's not a permanently standalone orphan in an otherwise cohesive system.

## 7. `shua_gym` and `shua_crypto` have no spec yet, but already have architectural implications worth flagging early
Both are only "TBD" stack entries in the roadmap, but two things are already knowable and worth deciding before their specs get written:
- **`shua_gym`** is described as MediaPipe pose streaming — that's a meaningfully heavier CPU/possibly GPU workload than the other modules, and the Pi 5 is the only compute target mentioned anywhere for backend modules. Worth deciding now whether pose estimation actually runs on the Pi 5 (checking against the same 8GB RAM budget as everything else — see the Rust Governor suggestions doc) or whether it's a candidate for the "laptop offload node" pattern that's already designed into the AI Router for Ollama models.
- **`shua_crypto`**, as a decentralized vault and key manager, is a fundamentally different trust category than a diary or resume tool — losing a diary entry is sad, losing a crypto key because of the current no-auth Governor trust model (see the Rust Governor suggestions doc, §1 of the main review) is a direct financial loss. Worth deciding whether `shua_crypto` gets its own, stricter auth/access model *before* it's built, rather than inheriting the same "Tailscale network is the only boundary" assumption as everything else by default.
